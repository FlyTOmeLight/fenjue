# Sol 与 Jev 路由分类实测

2026-10-13 的小样本结果支持继续用 Jev 做默认分类器。通过 Codex App Server 调用 `gpt-6.1-sol / low` 可以完成分类，但没有观察到最终档位选择的改善，成功配对样本的延迟中位数约为 Jev 的 11 倍，总 token 约为 3.16 倍。Sol 对一条纠错请求的细分类更符合预设标签；这条差异没有改变路由。

## 结果

下表采用关闭本地技能后的相同运行设置，共 15 对请求，其中 13 对双方成功。初始运行的技能上下文不同，单独保存，不混入本表。

| 指标 | Jev | Sol low |
| --- | ---: | ---: |
| 成功配对样本数 | 13 | 13 |
| 分类延迟 P50 | 0.732 秒 | 8.227 秒 |
| 分类延迟 P95 | 1.402 秒 | 16.205 秒 |
| 平均输入 token | 3,112 | 10,513 |
| 平均输出 token | 223 | 40 |
| 平均总 token | 3,335 | 10,553 |
| 最终档位符合预设 | 13/13 | 13/13 |
| 五项标签全部符合预设 | 11/13 | 12/13 |
| 包含未配对请求的成功数 | 14/15 | 14/15 |

失败单独保留：Jev 一次 `unavailable`，耗时 2.811 秒；Sol 一次超过 30 秒截止时间，耗时 30.026 秒。包含失败时，两边 P95 分别为 2.811 秒和 30.026 秒。调用顺序交替、串行执行。App Server 启动另外耗时 1.875 秒和 2.157 秒；请求延迟包含创建临时会话、分类和归档。

13 对成功样本中，Sol 输入共有 4,864 个缓存 token，输出包含 19 个 reasoning token，均已包含在输入或输出总数中。Jev 未提供这两项的计数，记为未知。不同服务的 tokenizer、计费和订阅额度计算不能通过此表直接换算。

两处标签差异值得区分：

- `failure-recovery:2`：“修复后仍会闪回旧结果”，Sol 判为纠错、多文件诊断；Jev 判为继续、局部诊断。两者都选择 Sol high。
- `ambiguity-and-quote:3`：“它那个地方再调整一下”，两者都识别出指代不明、信息缺失，并保留 high。预设 `reasoning=solution`，两者返回 `architecture`。这条标签本身存在解释空间，未在观察结果后修改标签。

初始运行取得 13 对成功结果：Jev/Sol 的 P50 为 0.601/8.636 秒，P95 为 0.725/12.839 秒，路由均符合预设。Sol 平均输入约 16,203 token。随后电脑闲置睡眠 426 秒导致一对请求中断；系统睡眠日志与中断持续时间吻合，这对请求不能用于推断正常服务延迟。关闭技能后，Sol 输入降至约 10,500 token，仍包含 Codex 运行环境提供的指令和工具定义。

## 方法与适用范围

使用 [16 轮合成数据](../evals/native-routing/sol-comparison.json)，覆盖跨系统设计、照方案实现、根因未知与已定位修复、失败反馈、机械整理、切换任务、敏感实现、引用指令和指代不明。数据及参考标签在请求前冻结。两边接收相同的五项问卷、当前请求、先前用户消息和预先给定的执行证据，不发送参考标签或未来证据。

Jev 使用现有分类接口；Sol 使用 Codex CLI 0.162.1 的常驻 App Server、每次新建 ephemeral thread、`low` 和 JSON Schema 输出约束。关闭本地技能、MCP 和可配置工具，不修改用户配置文件。仍残留的 Codex 系统上下文计入实际消耗，因此本次衡量的是当前 Codex 接入方式，不能推广为 Sol 裸 API 的固有成本。

两者的五项分类结果通过相同的 `balanced-native-v6` 规则映射到模型和 effort。为复用规则，标签被确定性地转换为 0/1 值；这些数值不是 Sol 的置信度。另行保留 Jev 真实概率经过现有规则得到的路由，本次成功样本也全部符合预设。

这是分类器比较：每轮各调用一次，固定历史输入，未运行生产会话中的延续快捷路径、任务切换二次分类、实际编码或自动专家审查。预设路由符合率不能代替任务完成率，也不能证明减少了多少人工切档。没有加入固定 Sol medium 基线。

累计尝试 58 次分类调用，覆盖全部 16 个独立轮次，15 个轮次在某次运行中得到完整配对。因中断没有完成原计划的两次全量重复；不据此声称结果稳定性。原始观测的精简版、失败记录、输入指纹和分批汇总见 [结果 JSON](../evals/native-routing/sol-comparison-results.json)。

## 复跑

只检查配置和调用预算，不调用模型：

```sh
npm run eval:compare:sol -- --repeats 1
```

真实运行需本机 Codex 登录及 Jev 的 API key。`--env-file` 只读取配置指定的 key，不将密钥写入报告：

```sh
FENJUE_CODEX_BIN=/opt/homebrew/bin/codex caffeinate -i npm run eval:compare:sol -- \
  --config fenjue.config.json --env-file /path/to/credentials.env \
  --live --repeats 1 --max-calls 32 \
  --out .fenjue/sol-comparison/rerun.json
```

`caffeinate` 适用于 macOS，仅在命令运行期间阻止闲置睡眠。每个输出文件只能新建；任一配对出现失败后保存结果并停止。`--max-calls` 限制本脚本发起的分类请求次数，不涵盖 Codex 内部可能发生的网络重试。

下一步若继续评估，应测疑难请求中增加 Sol 判断能否提高真实任务通过率，并计入额外耗时、总 token 和人工干预次数。当前结果没有支持把每轮路由全量换成 Sol。
